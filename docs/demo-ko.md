# 한국어 데모 시나리오

## 시작 화면 설명

“현재 계정과 두 리전, 모델을 먼저 확인하겠습니다. 앱, BMA와 Runtime은 버지니아 북부,
조회할 AWS 제어 API는 서울입니다. BMA는 Mantle의 `openai.gpt-6-luna` 모델을 사용합니다.
서울에서 조회한 정보 중 모델에 전달한 내용은 버지니아 북부에서 분석합니다.
샘플 모드에서는 실제 자원이나 모델을 호출하지 않습니다.”

실제 모드에서는 접속 키로 연결한다. 처음 계정 표시는 Web Function의 STS 결과이며,
첫 MCP 결과를 받은 뒤 Runtime 도구의 STS 확인으로 갱신된다.
화면의 계정 번호는 마지막 3자리만 보인다. 실제 계정 비교에는 원래 ID를 사용한다.
사용 모델은 Luna와 전체 모델 ID로 표시한다.
상단에서 다크 모드와 한국어/English를 전환할 수 있으며, 선택한 언어로 다음 답변을 생성한다.
답변은 생성되는 대로 Markdown으로 표시한다. 제목·표·목록과 코드가 렌더링되고,
조회 단계와 경과 시간이 보인다. 화면 폰트는 나눔스퀘어 OTF Bold다.
화면에는 실제 BMA 모델 ID `openai.gpt-6-luna`와 `us-east-1` 실행 리전이 표시된다.

## 1. EC2·RDS 인벤토리

**질문:** “서울 리전 EC2와 RDS 현황을 알려줘”

예상 절차: `aws-resource-inventory` → get_account_context → list_ec2_instances →
list_rds_instances.

“질문에 필요한 두 서비스만 조회했습니다. 반환된 리소스 수와 구성 상태를 보되,
페이지 완료와 잘림 여부를 같이 확인합니다. RDS가 available이어도 애플리케이션
정상을 확인한 것은 아닙니다.”

실행 기록의 도구명, 서울 대상 리전, 소요 시간, 결과 수를 펼쳐 API 이름과 UTC 시각을 확인한다.
실제 조회 수는 실행 결과를 읽어 설명하며 사전에 정해진 숫자를 말하지 않는다.

## 2. EC2 상태 점검

**질문:** “상태 점검에 실패한 EC2가 있는지 확인해 줘”

예상 절차: `aws-service-health` → 계정 확인 → EC2 목록 → 반환 ID에 대한
get_ec2_instance_health.

instance/system/attached EBS 상태 점검을 구분한다.
응답에서 빠진 ID는 “정상”이나 “존재하지 않음”으로 바꾸지 않는다.
샘플 fixture에는 impaired가 포함되어 있지만 실제 실행에 그런 자원이 있다고 가정하지 않는다.

## 3. ECS 실행 수와 배포

**질문:** “ECS 서비스의 실행 태스크 수와 배포 상태를 확인해 줘”

클러스터 목록을 찾고 그 범위에서 서비스 목록·DescribeServices를 조회한다.
desired/running/pending 및 배포 rollout 상태를 함께 읽는다.
목표 수보다 적은 실행 태스크가 보여도 배포 중인지 장애인지 추가 근거 없이 확정하지 않는다.
조회하지 않은 클러스터와 제한에 걸린 서비스는 따로 설명한다.

## 4. Lambda 오류와 스로틀

**질문:** “최근 한 시간 Lambda 오류와 스로틀을 확인해 줘”

Event Functions 목록에서 실제 이름을 얻은 후 요청·도구 한도 안에서 지표를 조회한다.
현재 배포는 목록 최대 2개, 라이브 검증은 첫 함수 1개의 최근 15분으로 제한한다.
반환된 UTC 시작·종료 시각, 300초 버킷, Errors·Throttles·Invocations를 확인한다.

“데이터가 없는 함수는 0건으로 계산하지 않습니다. 오류율도 분모와 같은 구간의
호출 수가 확보되지 않으면 만들지 않습니다. Web Functions는 이 목록에 포함되지 않습니다.”

샘플의 `sample-idle`은 의도적으로 지표가 비어 있어 이 차이를 보여준다.

## 5. ALARM 상태 목록

**질문:** “ALARM 상태인 CloudWatch 알람을 정리해 줘”

MetricAlarm과 CompositeAlarm을 함께 조회한다.
이름이 비슷하다는 이유로 특정 EC2나 함수의 장애와 연결하지 않는다.
알람 목록이 비어 있어도 “모든 서비스 정상”이라고 결론내리지 않는다.

## 6. 보고서 내보내기

**질문:** “조회 가능한 서울 리전 서비스의 운영 보고서를 작성해 줘”

`aws-operations-report`에 따라 서비스 현황, 주의 항목, 근거, 가설·추가 확인을 작성한다.
완료 후 **Markdown**, **HTML** 버튼으로 두 파일을 내려받는다.

“두 보고서는 같은 정규화된 근거를 담습니다. UTC 원본 시각과 Asia/Seoul 표시 시각이
별도로 있고, 권한 부족·부분 조회·미조회 서비스도 남습니다.
BMA가 버지니아 북부에서 처리하는 데이터 흐름도 표시했습니다.”

## 실패 사례 시연

계정 불일치·권한 거부는 운영 IAM을 변경해 만들지 않고 로컬 테스트로 재현한다.

```bash
.venv/bin/python -m pytest tests/test_inventory.py -k \
  'mismatched_account or access_denied or page_failure or no_cloudwatch_data or sensitive'
```

계정 불일치에서는 지역 서비스 클라이언트 자체가 호출되지 않는지,
권한 거부가 빈 결과로 보이지 않는지, 일부 서비스가 실패해도 성공한 근거가 남는지 확인한다.
추론 원문을 보여주려고 하지 않고 실행된 도구와 그 결과를 설명한다.


## BMA 운영 조사 이어가기

1. **운영 조사**를 선택하고 **서비스 상태 점검** 절차를 고른다.
2. “서울 EC2 목록을 최대 2개만 확인해 줘. 지금은 상태 점검하지 마.”라고 질문한다.
3. 진행 중 새로고침하고 접속 키로 다시 연결해 같은 조사 상태를 복구한다.
4. “앞서 조회한 첫 번째 EC2 한 개의 상태 점검만 확인해 줘.”라고 이어 묻는다.
5. “이전 관측 내용을 다시 조회하지 말고 요약해 줘.”라고 질문해 원본 시각과 재사용 안내를 확인한다.
6. 질문 이력에서 이전 답변을 열고 HTML 보고서를 미리 본다.

절차 단계 완료는 애플리케이션 정상 판정이 아님을 함께 설명한다.
